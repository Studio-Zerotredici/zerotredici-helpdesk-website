# Chatwoot v4.15.1-ce Branding Injection Points — Research Findings

Status: research complete, grounded in `vendor/chatwoot/` at pinned tag `v4.15.1`. No overlay files have been written yet — this is the input to `docs/BRANDING_FORK_PLAN.md`.

## Summary

Chatwoot CE already ships a **native, database-backed white-labeling system** for the four highest-value items — installation name, sidebar/login logo (light + dark), and the "Powered by" attribution link/text — driven entirely by the `installation_configs` table (seeded from `config/installation_config.yml`) and exposed to the frontend via `window.globalConfig` (injected server-side in `app/views/layouts/vueapp.html.erb`). Critically, these specific keys (`INSTALLATION_NAME`, `LOGO`, `LOGO_DARK`, `LOGO_THUMBNAIL`, `BRAND_NAME`, `BRAND_URL`, `WIDGET_BRAND_URL`, `TERMS_URL`, `PRIVACY_URL`) do **not** declare `locked: false` in the YAML, so per `InstallationConfig`'s `set_lock` default they load as `locked: true` — meaning they are **not** exposed in the Super Admin UI (`SuperAdmin::InstallationConfigsController#scoped_resource` filters to `editable` = `locked: false` only) and must be set directly via a Rails console / seed script against the `installation_configs` table, not via Dokploy environment variables or the admin UI. This changes the overlay plan: no frontend code overlay is needed for name/logo/attribution — only a one-time data-seeding step (rake task or `rails runner`) after first deploy. A real code overlay is still needed for: the primary brand color (SCSS custom properties, compiled at build time), the favicon/PWA icon set and `manifest.json` (static files under `public/`, not templated at all), and the two logo PNGs used in the login/marketing-adjacent `design-system` assets (unclear if reachable from the dashboard route, flagged below as unconfirmed).

## Native CE branding config confirmed (significant — changes overlay scope)

`vendor/chatwoot/config/installation_config.yml` lines 16-58 contain a full "Branding Related Config" block with these keys and their CE (non-enterprise) defaults:

- `INSTALLATION_NAME` = `'Chatwoot'`
- `LOGO_THUMBNAIL` = `'/brand-assets/logo_thumbnail.svg'`
- `LOGO` = `'/brand-assets/logo.svg'`
- `LOGO_DARK` = `'/brand-assets/logo_dark.svg'`
- `BRAND_URL` = `'https://www.chatwoot.com'`
- `WIDGET_BRAND_URL` = `'https://www.chatwoot.com'`
- `BRAND_NAME` = `'Chatwoot'`
- `TERMS_URL` = `'https://www.chatwoot.com/terms-of-service'`
- `PRIVACY_URL` = `'https://www.chatwoot.com/privacy-policy'`
- `DISPLAY_MANIFEST` (boolean) = `true` — description literally says "Display default Chatwoot metadata like favicons and upgrade warnings"; setting this `false` suppresses the whole PWA-icon/apple-touch-icon block in `vueapp.html.erb` (lines 8-30), which may be a cheap way to hide the hardcoded static favicon set entirely rather than replacing it.

This is **not gated behind Enterprise** — nothing in `enterprise/` overrides `GlobalConfig`, `InstallationConfig`, or these YAML keys (not verified exhaustively against every `enterprise/` file, but the file comment at `installation_config.yml` line 12 explicitly distinguishes `premium` as a separate flag that none of these branding rows use).

**However**, per `app/models/installation_config.rb` line 61 (`set_lock` defaulting `locked = true` when unspecified) and the YAML file's own header comment (lines 10-11: "if you don't specify locked attribute in yaml, the default value will be true... locked... won't be available in `super_admin/installation_configs`"), **none of the 9 branding keys above specify `locked: false`**, so all 9 are `locked: true` by default and will NOT appear in the Super Admin → Installation Configs UI. They must be set by directly creating/updating `InstallationConfig` rows (e.g. via `rails runner` or a custom rake/seed task), not through any UI, and not through Dokploy environment variables (confirmed: `dashboard_controller.rb`'s `set_global_config` calls `GlobalConfig.get(*GLOBAL_CONFIG_KEYS)`, which reads `InstallationConfig` DB rows via `lib/global_config.rb`'s `db_fallback`, not `ENV` — contrast with `lib/global_config_service.rb`'s `GlobalConfigService.load`, which DOES fall back to `ENV.fetch(config_key)` on first load, but that helper is used elsewhere for things like `SLACK_CLIENT_ID`/`FIREBASE_PROJECT_ID`, not for the branding keys, which are read via plain `GlobalConfig.get` in `dashboard_controller.rb`).

## Recommended overlay file list

Based on the above, the `branding/` directory (per `BRANDING_FORK_PLAN.md`'s overlay architecture) should contain:

1. **`branding/public/brand-assets/logo.svg`**, **`logo_dark.svg`**, **`logo_thumbnail.svg`** — Studio Zerotredici logo replacing the three files at `vendor/chatwoot/public/brand-assets/*.svg`. (Optional if instead repointing the `LOGO`/`LOGO_DARK`/`LOGO_THUMBNAIL` config values to different filenames via the seed step below — either approach works; replacing in place is simpler since the default config values already point here.)
2. **`branding/public/favicon-16x16.png`, `favicon-32x32.png`, `favicon-96x96.png`, `favicon-512x512.png`, `favicon-badge-16x16.png`, `favicon-badge-32x32.png`, `favicon-badge-96x96.png`** — replace the static favicon PNGs (not config-driven, per Finding 5).
3. **`branding/public/apple-icon-*.png`, `android-icon-*.png`, `ms-icon-144x144.png`** — the full Apple/Android touch-icon set referenced by literal path in `vueapp.html.erb` lines 16-29 (exact filenames need enumerating from `vendor/chatwoot/public/` at overlay-build time; not individually listed here since they weren't all read/verified above — do this enumeration during implementation, not by guessing the sizes).
4. **`branding/public/manifest.json`** — full replacement of the file, changing `"name"` and `"short_name"` from `"Chatwoot"` (currently hardcoded, lines 2-3) to Studio Zerotredici's values, keeping the same `icons` array structure pointed at the overlaid PNGs above.
5. **`branding/app/javascript/dashboard/assets/scss/_next-colors.scss`** — full or partial replacement of the CSS custom-property values (at minimum the `--iris-*` scale, lines 19-30 and its dark-mode re-declaration further down the file) with Studio Zerotredici's palette. This is the one file where a genuine line-by-line diff against upstream will be needed on every version bump — flag for extra scrutiny during upgrades.
6. **A seed script, not a file overlay** — e.g. `branding/seed_installation_config.rb` run via `rails runner` (or wired into a post-deploy Dokploy hook) that sets the 7 relevant `InstallationConfig` rows (`INSTALLATION_NAME`, `BRAND_NAME`, `BRAND_URL`, `WIDGET_BRAND_URL`, `LOGO`, `LOGO_DARK`, `LOGO_THUMBNAIL`, optionally `TERMS_URL`/`PRIVACY_URL`) with `locked: false` so they're also editable later via Super Admin without needing this script re-run on every deploy. This is NOT a file to copy into a fresh `vendor/chatwoot` checkout at build time (per the Dockerfile build recipe in `BRANDING_FORK_PLAN.md`) — it's a one-time (or idempotent, re-runnable) runtime data step against the running Postgres instance, most naturally executed once after first deploy, documented in `docs/DEPLOYMENT_GUIDE.md` rather than baked into the image.

**Open item carried forward**: item 1 in the findings table (whether the login screen, as distinct from the authenticated dashboard sidebar, actually reads `LOGO`/`LOGO_THUMBNAIL` the same way) was not conclusively verified — no dedicated login Vue component was found by filename search. Confirm this visually against a running v4.15.1 instance (or via further `grep` for the specific login route's Vue file) before assuming the login screen is covered by the same `Logo.vue` component and `globalConfig` mechanism as the sidebar.
